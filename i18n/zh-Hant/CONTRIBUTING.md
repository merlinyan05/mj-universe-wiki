# 貢獻指南

歡迎補充一個名字、一條留言、一個影片時間點，或者糾正一個字。留言區的新版本也可以收錄，不要求先成為「公認正史」。

## 不會 Git 也能參與

### 只提供線索

在 GitHub 倉庫開啟 **Issues → New issue**，選擇「補充設定或來源」或「糾錯與版本差異」。說明看到了什麼、在哪裡看到、涉及誰；最好附上原連結和時間點或留言上下文。

暫時找不到原連結也可以提 Issue，明確標記「待核對」。維護者會先作為線索處理，不直接寫成已核對的片內事實。

### 直接用網頁修改

1. 開啟相應人物或其他條目的 `.md` 檔案，點擊編輯按鈕。
2. 沒有寫入權限時，按 GitHub 提示 Fork 並在自己的副本編輯。
3. 完成後填寫簡短提交說明，提出 Pull Request。
4. 在 PR 裡寫清改了什麼、來源是什麼；等待維護者審閱。

無需安裝 Python 才能編輯文件。自動檢查結果會出現在 PR 裡。

## 使用 Git 提交

先在 GitHub 點擊 **Fork**，複製自己 Fork 的複製位址。以下位址中的 `YOUR-USERNAME` 請替換成自己的帳號；如果更改了 Fork 名稱，也相應替換倉庫名稱。

```bash
git clone https://github.com/YOUR-USERNAME/mj-universe-wiki.git
cd mj-universe-wiki
git switch -c docs/add-character-detail
# 修改相關條目；新增檔案時同步更新對應 README 索引
python3 scripts/check_docs.py
git add characters/ sources/
git commit -m "docs: 補充人物關係的來源"
git push -u origin docs/add-character-detail
```

之後在 GitHub 的 Fork 頁面選擇 **Contribute → Open pull request**，確認目標是原倉庫的 `main`。

第一次向某個專案貢獻前，可以在 GitHub 的 Settings → Emails 中查看自己的 `noreply` 電子郵件，並為本機倉庫設定：

```bash
git config user.name "你的公開署名"
git config user.email "從 GitHub 設定中複製的 noreply 電子郵件"
```

請填寫真實可用的設定值再提交，不要直接使用範例文字。這樣可以用公開署名參與，不必暴露私人電子郵件。

GitHub 操作參考：[Fork 與 PR 流程](https://docs.github.com/en/get-started/exploring-projects-on-github/contributing-to-a-project)、[提交電子郵件設定](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address)。

## 內容放在哪裡

| 內容 | 維護位置 | 新增條目時 |
| --- | --- | --- |
| 人物、父母、後代、別名、身分版本 | `characters/人物名.md` | 複製人物範本，更新人物索引 |
| 搭檔、師生、CP、關係不明的姓名 | `relationships/` | 明確關係方向和適用版本，更新索引 |
| 世界規則與宇宙差異 | `universes/宇宙名/README.md` | 引用人物檔案，不按宇宙複製人物 |
| 經典梗、口頭禪和使用對象 | `memes/` | 寫清誰對誰使用、在什麼情境下 |
| 宇宙專屬故事模式 | `universes/宇宙名/patterns/` | 說明觸發、升級與後果，附片例並更新索引 |
| 可跨宇宙重複使用的模式 | `universes/patterns/` | 標註典型宇宙、可重複使用範圍與差異；其他宇宙只連結 |
| 原片、留言、彈幕的觀察記錄 | `sources/` | 複製來源範本，分配未占用編號並更新來源索引 |

來源編號按現有編號遞增，不重排舊編號。若同時有人用了同一個新編號，在 PR 審閱時協調即可。姓名以人物檔案為唯一維護位置，其他頁面連結該檔案，避免維護多份衝突名單。

人物定位、性格、行為習慣、說話方式和不同宇宙的表現也歡迎補充；每條歸納附具體行為片例，避免只有「聰明／腹黑」等空泛標籤。客串寫明採用哪個人物版本，不自動繼承該版本的所有關係。

範本：[宇宙](templates/宇宙模板.md) · [故事模式](templates/故事模式模板.md) · [人物](templates/人物模板.md) · [來源](templates/来源模板.md) · [單條設定](templates/设定模板.md)。只補現有條目的一行時，不必複製整份範本。

## 圖片與表情包怎麼提交

### 人物三視圖與外觀參考

現有入口見[人物檔案的外觀參考](characters/README.md#外觀參考)。在對應 `characters/人物名.md` 的「外觀參考（外鏈）」中補充來源頁面、作者或發布方（已知時）、電影／遊戲／同人／MJ 作者版本、實際視角、核對日期與範圍，以及許可是否已確認。優先連結官方或作者原頁面；使用圖庫入口時註明是圖庫收錄，不把圖庫當作原作者。三視圖與一般多角度展示分別寫清。

授權未確認時僅添加普通文字連結，不下載入庫、不用 Markdown 圖片語法嵌入遠端原圖。不要宣稱可自由轉載、商用或用於 AI 生成；參考連結不是授權證明，也不作為 MJ 原片外觀或人物關係的考據證據。若以後提交自繪或 AI 生成的參考圖，註明社群創作版本、創作方式和第三方角色權利邊界，並按下方配圖規則審核。

### 先說明圖片幫助理解什麼

本倉庫整理 MJ 宇宙的設定，圖片服務於人物、關係、世界線、經典梗的理解或 Wiki 展示。提交時請回答：**這張圖幫助讀者理解了哪條設定，或承擔什麼明確的展示用途？**

| 可以隨條目收錄 | 如何說明用途 |
| --- | --- |
| README 封面、人物識別圖、關係圖、世界線示意圖 | 指明展示位置或關聯條目；自行繪製、AI 生成的示意圖與原片證據分開註明 |
| 佐證具體設定或經典梗的截圖 | 連結對應條目，記錄原連結、時間點或留言上下文、作者版本與實際核對範圍 |
| 必須透過動作才能理解的簡短 GIF | 解釋靜態圖無法表達的動作，只保留說明該條目所需的片段 |

泛漫威表情包、桌布、Q 版貼圖和其他通用素材合集，以文字索引與外鏈介紹。即使素材有轉載授權，也需要符合上述內容範圍才隨條目入庫。僅說明「以後做影片可能用得上」不足以說明它與設定的關係。

### 通用素材合集採用索引與外鏈

可以在 `memes/` 增加素材索引，並連結外部存放位置或獨立素材倉庫；無需先把整包圖片提交進本倉庫。索引寫清合集名稱、覆蓋角色或主題、與設定集的關係、存取連結、來源及權利狀態，以及數量和內容實際核對到了什麼範圍。只有整理者提供的數字，應標明「由整理者提供，尚未逐項核對」。

外鏈不代表本倉庫已經逐圖審核，也不授予素材使用權。索引仍需說明它對查詢設定或相關創作有什麼具體幫助，避免堆積無關連結。

### 條目配圖的提交方式

梗配圖可以放在 `memes/images/角色名/`，例如 `memes/images/灭霸/emo_reply.jpg`；封面及 Wiki 展示圖可以放在 `assets/images/`。在對應條目中用相對路徑展示圖片，例如：

```markdown
![傷感文案被接成外號的留言截圖](images/灭霸/emo_reply.jpg)
```

範例路徑不代表已經收錄該檔案，請替換為實際提交圖片。每張入庫圖片都要能從條目或清單定位，並記錄關聯條目或展示用途、原連結或生成說明、創作者（已知時）、適用版本、實際核對範圍，以及轉載許可或授權依據。新增素材索引時，將索引加入 `memes/README.md`。

依照[第三方資料說明](ATTRIBUTION.md)，符合收錄範圍的原創或有明確轉載授權的圖片可以隨 PR 提交；尚未確認轉載授權的網路搜圖先收錄來源連結和文字索引。來源連結、第三方版權聲明與轉載授權分別說明，不把第三方素材自動改用本倉庫的 CC 授權。提交前也請檢查圖片中的私人資訊。

### 檔案格式與檢查

支援 JPG／JPEG、PNG、GIF 和 WebP。副檔名應與真實格式一致；需要動畫或透明通道時，請核對原始素材，給靜態 JPEG 換副檔名或轉存格式不會恢復動畫或透明通道。

純圖片目錄不用逐層新建 README；含 Markdown 資料的目錄仍需 README 索引。圖片連結會檢查檔案是否存在。校驗腳本按二進位讀取上述圖片格式並核對檔案頭；**腳本通過只表示通過技術檢查，收錄用途、來源、版本與權利狀態仍需人工審核。**

可在本地執行以下檢查，不需要安裝第三方 Python 套件：

```bash
python3 scripts/check_docs.py
python3 -m unittest discover -s tests -v
```

## 一條有用的貢獻長什麼樣

例如已有來源記錄 [R09](sources/R09.md) 保存了「綠巨人父親叫綠豆湯」的留言觀察：

- 關係：綠巨人 → 父親 → 綠豆湯。
- 類型：留言共創；不標成片內對白。
- 位置：原影片的公開留言，說明回覆上下文；無穩定留言連結時連結影片頁。
- 版本：保留其他父親名字，不把某條留言升級成唯一名單。

這個例子引用已有資料，不代表新貢獻者已經重新核對原頁面。實際提交時請說明自己看到了標題、留言、圖片、片段還是完整影片。

## 來源類型與版本差異

| 標籤 | 含義 |
| --- | --- |
| 片內設定 | 對白或畫面明確表達，盡量提供時間點 |
| 作者補充 | 簡介、置頂留言或作者回覆 |
| 留言共創 | 網友接龍、彈幕、猜測、留言圖片 |
| 整理推斷 | 根據材料提出解釋，明確依據與不確定性 |
| 原創擴寫 | 新創作版本，不能寫成已有作品的事實 |
| 待核對線索 | 暫缺出處或僅有間接線索，可先提 Issue |

關係不明就保留不明；版本衝突就並列，說明作者、分支或單集。名字出現不自動證明爸爸、媽媽或其他輩分；自動字幕同音字也需保留不確定性。失效來源保留原連結與此前核對範圍，不無來源地改寫結論。

## 審閱與維護

一條 PR 盡量圍繞一個人物、來源或話題；錯別字可以直接改。維護者關注來源邊界、相互連結和版本差異，不因某個版本不符合個人偏好就刪除它。

普通貢獻者 push 到自己的 Fork。獲得寫入權限的維護者可直接 push 主題分支後提 PR；授權寫入權限和 `main` 分支保護需要倉庫上線後在 GitHub 設定，不由本機文件自動生效。推薦 `main` 經 PR 合併，並要求 `docs-check` 通過。

## 授權與隱私

提交原創整理即表示同意將自己有權授權的這部分內容按 [CC BY-SA 4.0](../../LICENSE) 共享，保留自己的署名權；無須轉讓著作權。沒有權利授權的第三方內容，只保留必要短摘錄、概括及來源，並明確歸屬。詳見[署名說明](ATTRIBUTION.md)。

不要提交私人聊天、真實家庭資料、帳號憑證、本機絕對路徑或無關個人資訊。可保留用於溯源的公開創作者署名；不額外蒐集留言者的聯絡方式、個人簡介等資訊。也請尊重不同貢獻者，圍繞資料本身討論。

## 記錄同名親屬的不同版本

父母表裡出現衝突時，優先補「作者／具體作品＋親屬方向＋原字形＋定位」，不要選一個名字覆蓋全部。例如同一字面名字在不同作品分別是哥哥、爺爺時，兩條分別保留；歌曲、上傳者配圖、片內自述與留言接龍也分類型記錄。

新證據能確認此前待核關係時，在人物檔案補新來源，在舊候選頁註明已補證；保留舊來源當時只讀到標題／留言的範圍。按需同步人物索引、關係頁與宇宙入口，避免一頁已確認、另一頁仍籠統寫全都未核實。

單集臨時職務、騙詞中的權威稱呼、借用證件的身分不能直接升級為永久人物屬性。跨宇宙客串註明來客和當地人的區別，具體片例見[客串說明](universes/跨宇宙与客串.md)。
